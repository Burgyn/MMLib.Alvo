:::tip[What you will achieve]
Alvo inside your own ASP.NET Core app: the generated API under a prefix of your choice, beside your own routes, driven by
the same descriptor the Docker image serves. About fifteen minutes, starting from an existing web project on .NET 10.
:::

## Before you start

- The .NET 10 SDK and an ASP.NET Core project (`dotnet new web` is enough), plus a clone of the repository: Alvo is
  pre-v0.1 and **no package is on NuGet yet**.
- A descriptor. The code below uses `examples/vehicle-registry`; [Run your own descriptor](/MMLib.Alvo/start-here/run-your-own/)
  is the Docker-only way to try one first.

## 1. Reference the packages

Two packages are the minimum: `MMLib.Alvo`, the core (schema registry, Data API, rule engine, events, management),
and one database driver, `MMLib.Alvo.Data.Sqlite` or `MMLib.Alvo.Data.PostgreSql`. The core never references a driver;
the driver you add is the one you select in code. Every package is listed in the [C# API reference](/MMLib.Alvo/reference/csharp/).

Today you either reference the projects in a clone or install from a local package feed you pack yourself;
`dotnet add package` from NuGet works from v0.1.

## 2. Register Alvo

The embedded sample, [`samples/MMLib.Alvo.Samples.EmbeddedHost`](https://github.com/Burgyn/MMLib.Alvo/tree/main/samples/MMLib.Alvo.Samples.EmbeddedHost),
is a fleet-desk app that keeps its records in Alvo. Its registration is the pattern to copy. `AddAlvo` is the one entry
point: `UseSqlite` selects the database, `FromDescriptor` supplies the descriptor, and `AddDataApi` mounts the generated
API under `/api/alvo` so it never collides with the app's own routes. The last line registers a CEL function written in
C#, which the descriptor's hooks may call.

<SourceExcerpt code={sampleHost} from="builder.Services.AddAlvo(alvo => alvo" to="NormalizeVinSummary));" dropComments={true} title="SampleHost.cs" />

There is no call to apply the descriptor: `AddAlvo` registers a hosted service that brings the schema up before the app
starts serving, and `/health/ready` answers 200 once it has.

The API keys come from configuration. The sample declares one dev key in `appsettings.json`, deliberately without a
secret, and binds the section:

<JsonExcerpt code={appsettings} pointer="/Alvo/Auth" title="appsettings.json" />

<SourceExcerpt code={sampleHost} from="builder.Services.Configure<AlvoAuthOptions>" to="builder.Services.Configure<AlvoAuthOptions>" title="SampleHost.cs" />

Alvo refuses to start without a secret of at least 32 characters, so the app cannot ship a working default credential.
Supply it outside source control, as step 4 does with user secrets.

## 3. Map the endpoints

Mapping is a separate step, so the routes land exactly where your pipeline wants them:

`MapAlvoHealth` maps `/health/live` and `/health/ready`, and comes first because `MapAlvoDataApi` refuses a host whose
Data API services are absent. `MapAlvoDataApi` returns a convention builder over Alvo's generated routes and nothing
else, so you can attach your own rate limiting, telemetry or tags to them.

## What your host still owns

Alvo adds no authentication, authorization or routing middleware on your behalf. Three things stay yours:

- **Authentication of your own users.** Alvo's generated API authenticates its own API keys. Your app's cookie or token
  users reach the same data through your own endpoints, which pass Alvo the caller and let the descriptor's rules
  decide: [Use your own authentication](/MMLib.Alvo/guides/own-authentication/).
- **Error rendering.** The sample deliberately does not call `AddAlvoProblemDetails()`, because an embedded host owns
  the shape of its error responses. Without it, Alvo's endpoints still answer their own refusals as problem documents,
  but three problem types are only produced with it: `unreadable-request`, `internal` and `function-failed`
  ([Problem types](/MMLib.Alvo/reference/problem-types/)).
- **Your own endpoints.** They call Alvo in process through `IAlvoData`, with no HTTP round trip and no second
  authorization model: [Call Alvo from your endpoints](/MMLib.Alvo/guides/call-from-endpoints/).

:::caution[Not in this build]
A host cannot yet publish its own signed-in user to the generated `/api/alvo` routes: they authenticate the API-key
header only, so your users go through your own endpoints. Do not point `Alvo:Auth:HeaderName` at `Cookie` to get
around it; Alvo refuses that at startup, because it would make every generated route a cross-site request forgery
target. The seam is planned for a later phase ([#210](https://github.com/Burgyn/MMLib.Alvo/issues/210)).
:::

## What can go wrong

| Status | Problem type | When | Fix | Returned by |
|---|---|---|---|---|
| 401 | [`unauthenticated`](/MMLib.Alvo/reference/problem-types/#unauthenticated) | An API key was sent to `/api/alvo` and cannot be used: a wrong secret, or a role the descriptor does not declare. | Use the secret you configured; give the key only roles in `auth.roles` or built in. | every host |

If the app stops at startup instead, the message names the option it refused, such as a dev key with no secret, and
what to set.
