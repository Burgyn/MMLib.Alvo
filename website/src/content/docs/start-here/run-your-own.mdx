:::tip[What you will achieve]
Your own descriptor behind the standalone stack (Alvo over PostgreSQL), with API keys that work for the roles it
declares. A few minutes with Docker and git, and no .NET SDK, starting from a clone of the repository.
:::

## Before you start

- Docker with Compose v2, git, `openssl`, and a clone of the repository: `git clone https://github.com/Burgyn/MMLib.Alvo`.
  Run every command from the clone root.
- A descriptor file. If you do not have one yet, the commands below use
  [`examples/help-desk`](https://github.com/Burgyn/MMLib.Alvo/blob/main/examples/help-desk/help-desk.alvo.json), and
  [Start from an example](#start-from-an-example) copies `examples/simple-tasks` as a starting point.

## 1. Declare keys your descriptor knows

The stack's `docker-compose.yml` defines one dev key, `demo`, for the vehicle-registry demo. It carries the roles
`admin`, `authenticated` and `inspector`, and **a key with one role the descriptor does not declare authenticates
nothing**: every request with it is a 401 `unauthenticated`. A key's roles must be listed in the descriptor's
`auth.roles` or be built in (`authenticated` and `admin` are). So declare keys for your own roles in a compose
override.

Save this as `docker-compose.override.yml` in the clone root. Compose merges that file into `docker-compose.yml`
automatically, and the repository ignores it, so your keys never show up in `git status`:

<Code code={override} lang="yaml" title="docker-compose.override.yml" />

It adds two keys for `help-desk`, whose `auth.roles` are `admin` and `agent`: `agent` (roles `agent`,
`authenticated`) and `admin` (roles `admin`, `authenticated`). Change the `KeyId`s and roles to your
descriptor's. Each secret is read from a variable, and the `:?` form makes compose refuse to start without it
rather than invent one; a secret must be at least 32 characters.

The same file sets up the dashboard's bootstrap administrator, `admin@example.com`. Its password is read from a mounted
file, `.alvo-admin-password` in the clone root, never from a variable; the repository ignores that file too.

## 2. Point the stack at your descriptor

`ALVO_DESCRIPTOR` picks the descriptor the stack mounts. Unset, it is `examples/vehicle-registry`, the
[Quick start](/MMLib.Alvo/start-here/quick-start/)'s demo. The path is relative to the clone root, or absolute.

<Steps>

1. Copy the override, generate the password file and the three secrets, choose the descriptor, and start the stack:

   <Code code={runYourOwn.trimEnd()} lang="sh" title="Terminal" frame="terminal" />

   `--wait` returns once the API is ready, which means the descriptor is applied. The last command lists the tickets
   with the `agent` key: an empty page, because nothing has been written yet.

2. Every compose command reads `docker-compose.yml` again, `down` included, so keep these variables exported in the
   shell you use for the stack, or put them in a `.env` file in the clone root (also ignored).

</Steps>

The API is at `http://localhost:8080/api/<entity>`, its OpenAPI document at `/openapi/v1.json`, an API browser at
`/scalar`, and the dashboard at `/admin`. The
[Tutorial](/MMLib.Alvo/start-here/tutorial/) walks through this exact stack one change at a time.

## 3. Change it

Edit the descriptor, then recreate the `alvo` container so it reads the file again:

<Code code={applyChange.trimEnd()} lang="sh" title="Terminal" frame="terminal" />

On start, Alvo compares the descriptor with the schema it applied before. A change that discards nothing (a new entity,
a new field, a changed rule) is applied; one that would drop or narrow data is refused, and the container stops with
the plan in its log. To apply without a restart, send the descriptor to the Management API instead; both paths, with
dry runs, revisions and rollback, are in [Apply and evolve your descriptor](/MMLib.Alvo/guides/apply-and-evolve/). In
this build only rule and hook changes take effect that way at once: a new entity or field reaches the Data API after a
restart ([#103](https://github.com/Burgyn/MMLib.Alvo/issues/103), [#353](https://github.com/Burgyn/MMLib.Alvo/issues/353)).

## Start from an example

`examples/simple-tasks` is the smallest real backend: projects and the tasks inside them, owned by the user who created
them. Copy it, and from then on it is your descriptor:

<Code code={simpleTasks.trimEnd()} lang="sh" title="Terminal" frame="terminal" />

`my.alvo.json` in the clone root is ignored by the repository, like any `*.alvo.json` there. The first line deletes
the stack's database. A database holds the schema of the descriptor it served; starting a
different descriptor over it would drop the old tables, and Alvo refuses that (see [What can go wrong](#what-can-go-wrong)).

`simple-tasks` declares no `auth.roles`, so of the override's keys only `admin` works there (its roles are both built
in); the `agent` key answers 401 until you add `"roles": ["agent"]` to the descriptor's `auth` block, or remove `agent`
from the key.

## What can go wrong

| Status | Problem type | When | Fix | Returned by |
|---|---|---|---|---|
| 401 | [`unauthenticated`](/MMLib.Alvo/reference/problem-types/#unauthenticated) | The key carries a role the descriptor does not declare (the built-in `demo` key over any descriptor without `inspector`), or the secret is wrong. | Give the key only declared or built-in roles; export the same secret the stack was started with. | every host |

**The stack does not start.** `docker compose up --wait` fails and the `alvo` container has exited. Read why:

<Code code={logs.trimEnd()} lang="sh" title="Terminal" frame="terminal" />

The end of the log says what to change. The common reasons:

- **The descriptor is invalid.** The log shows `Descriptor validation failed:` and one line per problem: its JSON
  pointer, for example `/entities/tickets/fields/estimate_cost/computed`, what is wrong and how to fix it. Correct the
  file and start again.

  :::caution[Known issue in this build]
  This refusal arrives as an unhandled `DescriptorValidationException`, and the container exits with code 139
  instead of the clean exit 78 below ([#340](https://github.com/Burgyn/MMLib.Alvo/issues/340)). The messages are
  the same.
  :::
- **The change would discard data.** The log says `Alvo cannot start:`, lists the plan with the destructive steps
  marked (such as `DropEntity tickets`), and the container exits with code 78. Keep what the descriptor dropped, or,
  if the data is disposable, start over with an empty database:

  <Code code={tearDown.trimEnd()} lang="sh" title="Terminal" frame="terminal" />

- **A variable is missing.** Compose itself refuses, naming the variable (`set ALVO_AGENT_KEY_SECRET before starting
  the stack`), before any container starts. Export it again.
