:::tip[What you will build]
Two credentials for Acme Repairs. A **service token** lets the billing system read Acme's completed jobs and nothing
else, and it keeps working while technicians come and go. A **personal token** lets Dana's nightly script read and
create jobs as Dana, without a browser and without her Google account. About fifteen minutes, starting from the Acme
Repairs backend in [Tenants, members and invitations](/guides/tenants-and-invitations/).
:::

## Before you start

- The Acme Repairs stack from [Tenants, members and invitations](/guides/tenants-and-invitations/), with Acme
  created and Dana signed in on the page. Dana owns Acme and is its dispatcher. Tokens are minted by a signed-in
  person, never by another token.

**Apply step 1 in place.** Turning tokens on changes no table, so Acme, Dana and Theo stay. Add the line to
`acme-repairs.alvo.json`, then recreate the container so it reads the edited file:

```sh title="Terminal"
docker compose up --wait --wait-timeout 90 --force-recreate alvo
```

**Send Dana's requests from her window**, with `api()` in the browser console, as in the
[tenants guide](/guides/tenants-and-invitations/#before-you-start). A token is what another system holds, so try it
the way that system would: from a terminal, without the page, with the `token` step 2 answers in `BILLING_TOKEN`:

```sh title="Terminal"
curl -sS 'localhost:8080/api/work_orders?status=eq.completed' -H "X-Alvo-Api-Key: $BILLING_TOKEN"
```

`{tenantId}` below is Acme's id and `{keyId}` a token's public id. Each step names the case of
`test/teapie-field-service/170-SelfService` that runs it against the field-service demo. That suite runs the fuller
field-service descriptor (more fields, a state machine), so its requests carry more than the ones shown here; the
answers are the same.

## Build it

<Steps>

1. **Turn tokens on.** One line in `auth`:

   <Code code={accessTokens} lang="json" title="acme-repairs.alvo.json" ins={[9]} />

   [`personal`](/reference/descriptor/auth/#auth.accessTokens.personal) and
   [`service`](/reference/descriptor/auth/#auth.accessTokens.service) are off unless you say so.
   [`maxLifetimeDays`](/reference/descriptor/auth/#auth.accessTokens.maxLifetimeDays) (1–365, default 90) is the
   furthest ahead a token's expiry may be. Every token expires. A service token acts as a shared tenant, so the apply
   refuses `"service": true` without `tenancy.selfService.createTenants`, at `/auth/accessTokens/service`.

2. **Mint them.** Dana mints the billing system's token. It acts in Acme with the `dispatcher` role, and its scope
   lets it read jobs only:

   ```http
   POST /auth/v1/tokens
   Authorization: Bearer <Dana's access token>
   Content-Type: application/json

   {
     "name": "billing",
     "kind": "service",
     "tenantId": "3c9e…",
     "roles": ["dispatcher"],
     "scopes": ["work_orders:read"],
     "expiresAt": "<28 days from now>"
   }
   ```

   ```http
   HTTP/1.1 201 Created

   {
     "keyId": "alvo_svc_7fQx…",
     "token": "alvo_svc_7fQx….Lw3k…",
     "header": "X-Alvo-Api-Key",
     "kind": "service",
     "name": "billing",
     "tenantId": "3c9e…",
     "roles": ["dispatcher"],
     "scopes": ["work_orders:read"],
     "expiresAt": "…",
     "createdAt": "…"
   }
   ```

   **`token` is in this answer and in no other, ever.** Put it in the billing system's secret store now. Alvo keeps
   only a hash of it. `header` names the header to send it in.

   `expiresAt` is required and is computed when you mint, never written down: RFC 3339 with an offset, later than now
   and at most `maxLifetimeDays` ahead, or the mint is refused at `/expiresAt`. Here it is 28 days, inside the
   descriptor's 30:

   ```js
   const expiresAt = new Date(Date.now() + 28 * 24 * 60 * 60 * 1000).toISOString();
   ```

   ```sh
   date -u -d '+28 days' +%Y-%m-%dT%H:%M:%SZ   # GNU date; on macOS: date -u -v+28d +%Y-%m-%dT%H:%M:%SZ
   ```

   That value replaces `<28 days from now>` in the request. A service token's `roles` must be tenant roles its minter
   holds in that tenant, and only an owner mints one. (`170-SelfService/004-billing-token`, `DanaMintsBilling`.)

   Dana's own script gets a personal token. It has no `roles`: it holds whatever Dana holds in Acme, read on every
   request:

   ```http
   POST /auth/v1/tokens
   Authorization: Bearer <Dana's access token>
   Content-Type: application/json

   {
     "name": "nightly export",
     "kind": "personal",
     "tenantId": "3c9e…",
     "scopes": ["work_orders:read", "work_orders:write"],
     "expiresAt": "<28 days from now>"
   }
   ```

   The answer is the same shape, with a key id starting `alvo_pat_`. Without `tenantId`, a personal token acts as its
   person in no tenant, which is what a level-1 app such as the
   [time tracker](/guides/sign-in/) wants.

3. **Use them.** A token goes in **`X-Alvo-Api-Key`**, exactly where a configured API key goes. Its tenant was fixed
   when it was minted, so it needs no `X-Alvo-Tenant`:

   ```http
   GET /api/work_orders?status=eq.completed
   X-Alvo-Api-Key: alvo_svc_7fQx….Lw3k…
   ```

   ```http
   HTTP/1.1 200 OK

   { "items": [ { "id": "e41d…", "title": "Replace the kitchen tap", "status": "completed", … } ], … }
   ```

   Billing's write is refused before any rule is consulted. Its `dispatcher` role would allow creating a job, but its
   scope does not:

   ```http
   HTTP/1.1 403 Forbidden

   {
     "type": "https://alvo.dev/errors/out-of-scope",
     "status": 403,
     "detail": "The presented API key's scopes do not permit this operation. Grant the key the scope it needs.",
     …
   }
   ```

   **The mistake to avoid: sending a token as `Authorization: Bearer`.** `Bearer` is for a person's access token
   from sign-in. A personal or service token sent there is not one, and the answer is the generic refusal of an
   unusable session. **It does not tell you to use the other header**:

   ```http
   HTTP/1.1 401 Unauthorized
   WWW-Authenticate: Bearer error="invalid_token"

   {
     "type": "https://alvo.dev/errors/unauthenticated",
     "status": 401,
     "detail": "The presented bearer token could not be used. Sign in again, or check that it has not expired or been revoked and that you belong to the tenant you requested.",
     …
   }
   ```

   If an integration gets this with a token whose key id starts `alvo_pat_` or `alvo_svc_`, move the token to
   `X-Alvo-Api-Key`. A hint in the answer itself is [#539](https://github.com/Burgyn/MMLib.Alvo/issues/539). (`170-SelfService/004-billing-token` and `010-tokens-reach`, `BillingAsBearer` and its control
   `BillingAsKey`.)

   Dana's script creates jobs the same way, and **a scoped create still carries `tenant_id`** in its body, as every
   scoped create does today (see [step 3 of the tenants guide](/guides/tenants-and-invitations/) and
   [#538](https://github.com/Burgyn/MMLib.Alvo/issues/538)). The rows it writes
   show Dana in `created_by`. The rows billing would write show the token's own id: a service token is a member of the
   tenant that nobody signs in as.

4. **List and revoke.** `GET /auth/v1/tokens` lists a person's personal tokens and the service tokens of every
   tenant they own: what each is, who minted it, and when it was last used. It never includes the secret:

   ```json
   [
     {
       "keyId": "alvo_svc_7fQx…",
       "kind": "service",
       "name": "billing",
       "tenantId": "3c9e…",
       "roles": ["dispatcher"],
       "scopes": ["work_orders:read"],
       "mintedBy": { "id": "5b1f…", "displayName": "Dana Novak" },
       "createdAt": "…",
       "expiresAt": "…",
       "lastUsedAt": "…",
       "revokedAt": null,
       "status": "active"
     }
   ]
   ```

   `DELETE /auth/v1/tokens/{keyId}` revokes one. It answers `204`, also the second time, and the token's next request
   is `401`. The minter may revoke their token, and so may any owner of a service token's tenant. `lastUsedAt` is
   accurate to about a minute. (`170-SelfService/004-billing-token`, `DanaListsTokens`.)

</Steps>

## How it behaves

### Personal or service

| | Personal token | Service token |
|---|---|---|
| Acts as | its person, in one tenant or in none | the tenant |
| `@user.id` and `created_by` | the person | the token's own id |
| Roles | the person's current tenant roles, read on every request | fixed when it is minted: at least one, each held by the minter then |
| Who mints it | any signed-in person | an owner of a shared tenant |
| Dies when | it expires or is revoked, the person leaves the tenant, or the person is banned | it expires or is revoked, or its minter stops being an owner (removed, demoted, leaves) or is banned |
| Use it for | a script, a CLI or an automation step that works as you | an integration that works for the team, whoever is in it |

**Scopes** limit a token on the Data API to whole entities: `<entity>:read` covers listing and reading,
`<entity>:write` covers creating, updating and deleting, and does not include reading. A token needs at least one, and
each must name an entity the descriptor declares. A wildcard such as `*:read` is refused, because it would quietly
grant every entity you add later. A person who wants everything uses their session. A request must pass the scopes
and then the entity's rules, so a scope never grants what the roles do not.

### When someone leaves

A token never outlives the reason it was allowed to exist. Each of these is a revocation, written in the same
transaction as the change that causes it:

- **A member is removed, or leaves.** Their personal tokens for that tenant die. The service tokens they minted for
  it die too. Dana removing Theo ends Theo's token on its next request, while billing keeps reading
  (`170-SelfService/005-member-removed`).
- **An owner is demoted.** The service tokens they minted die, because a service token's power was chosen by an
  owner. A remaining owner mints the replacement. The person's personal tokens keep working with their new, smaller
  roles.
- **A person is banned.** An operator disabling the account kills every token it minted, in every tenant
  ([Banning a person](/guides/sign-in/#banning-a-person)).
- **A token expires, or is revoked.**

**Dead stays dead.** Invite the removed person back, or enable the banned account, and their old tokens still answer
`401`. They mint new ones.

Changing a member's roles revokes nothing: a personal token simply holds the new roles on its next request. And the
descriptor decides on every request too. Switch `personal` or `service` off and every token of that kind is `401`
until you switch it back on.

### Where a token is refused

Tokens are for reaching data. They never manage anything:

- **Minting, listing and revoking tokens, and every tenant, member and invitation route**: `403`. Those are acts of a
  signed-in person, so a token cannot mint a token (`170-SelfService/010-tokens-reach`).
- **The Management API**: `403`, with "Personal and service tokens are app credentials and never manage a project.
  Use an operator session or a configured API key." This holds even if the token's roles would match an `access`
  level.
- **A host's own endpoints mapped with `.WithAlvoCaller()`**: `403` for now. Such an endpoint names no entity, so
  there is nothing to check the token's scopes against, and Alvo refuses rather than let a `work_orders:read` token
  act there with everything its roles allow. Letting an endpoint name the scope it needs is
  [#536](https://github.com/Burgyn/MMLib.Alvo/issues/536). A [command](/extending/commands/) bound to an entity does
  take a token that holds both `read` and `write` on that entity. A command bound to none takes no token.

## Limits and what is not here yet

- **Expiry**: at most `maxLifetimeDays` ahead, 90 by default and 365 at most. Lowering it bounds new tokens only.
- **100 live tokens per account.** The next mint is `409`.
- **Minting is rate-limited** with tenant creation: 10 a minute per client address together
  (`Alvo:Api:RateLimits:Create`), then `429`.
- **A token sent as `Authorization: Bearer` gets no hint** that it belongs in `X-Alvo-Api-Key` (step 3;
  [#539](https://github.com/Burgyn/MMLib.Alvo/issues/539)).
- **Scopes are entity × read/write.** Nothing finer, such as a field, an operation or "only my own rows".
- **No IP allow-list per token**, and no OAuth client credentials: a service token is an API key, not an OAuth client.
- **No events or audit trail** for minting and revoking yet.
- **Revoked and expired tokens are never cleaned up.** Every mint adds a row that nothing deletes yet
  ([#527](https://github.com/Burgyn/MMLib.Alvo/issues/527)).
