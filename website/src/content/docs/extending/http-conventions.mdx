- **A name the descriptor does not declare fails the route-table build** — on `MapAlvoDataApi()`'s builder — and
  readiness reports `Failed`. A typo is never a rate limit you believe you have.
- **The table is built once**, on the first routed request, against the descriptor applied then. Naming an entity the
  dashboard applies only later fails the Data API until the process restarts.
- **On a `MapGroup`** the Data API is mapped under, `ForEntity` cannot know the descriptor and checks no name, but it
  still reaches the entity's routes: its conventions are forwarded through the group's `Finally`, so they run after the
  route's own conventions. That works for metadata — rate limiting, authorization, `WithMetadata` — but not for an
  endpoint filter: a route's filters are composed before its `Finally` runs, so the filter could never run. A filter
  added through `ForEntity` on a group fails the route-table build and readiness reports `Failed`. Put it on
  `MapAlvoDataApi()`'s builder: `app.MapAlvoDataApi().ForEntity("rooms", r => r.AddEndpointFilter(…))`.
- **A named rate-limit policy is one partition** across every endpoint that names it. `RequireRateLimiting("rooms")` on
  two entities would share one budget. To limit each entity on its own, partition the limiter on
  `AlvoEndpointMetadata.Entity`:

Alvo sets it in the same call that attaches its authorization filter, so every route Alvo generates carries it together
with its gate. It is a public record, so an endpoint of your own can carry it too; it says which entity a route
serves, not that Alvo gates it.

## Alvo's gate stays on

A convention may add filters around Alvo's authorization filter. One that removes it — clearing or rebuilding
`EndpointBuilder.FilterFactories`, on `MapAlvoDataApi()`, in a `ForEntity`, or on a `MapGroup` the Data API is mapped
under — fails the route-table build: no routes, readiness `Failed`, and a critical log naming the route.

- **Commands too.** A command endpoint stripped of its access filter fails the host's start. The check runs once the
  request pipeline is built, over every command route.
- **`.WithAlvoCaller()` fails closed.** An endpoint stripped of Alvo's filter has an `AlvoCaller` that throws.
- **What the check sees.** It checks that the endpoint's request delegate was composed with Alvo's filter. A convention
  that assigns an endpoint's `RequestDelegate` outright replaces Alvo's handler with its own, and is outside what the
  check sees.

A `Finally` convention runs after the filters are composed, so it cannot remove the gate even when it clears the list.

## Commands are endpoints too

`MapAlvoCommand` returns a `RouteHandlerBuilder`: `.WithSummary`, `.RequireRateLimiting` and `.RequireAuthorization`
apply as on any endpoint. See [Commands and inbound webhooks](/extending/commands/).
