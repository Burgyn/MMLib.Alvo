An event handler is C# your host runs **after** a write commits: post to a chat, call an ERP, open a follow-up. It runs
on Alvo's transactional outbox, so it never undoes the write and is never lost with it — each matching event becomes a
**delivery** that is retried until it succeeds or is dead-lettered.

## Register a handler

Group registrations by entity with `Entity("name", …)` — or `Entities(["orders", "invoices"], …)`, or `Entity("*", …)`
for every entity — and pick the verb: `OnCreated`, `OnUpdated` (also a replace), `OnDeleted`, `OnSaved` (created or
updated).

<SourceExcerpt code={handlers} from="public static IAlvoBuilder AddTicketDeskHandlers" to="TimeSpan.FromSeconds(10)));" title="TicketDeskHandlers.cs" />

- **The id is the handler's identity.** Lower-case letters, digits and hyphens. Its deliveries are found by it after a
  restart, so renaming a handler is retiring the old id ([below](#rename-or-remove-a-handler)).
- **A delegate** takes the message — `AlvoCreated<AlvoRecord>` (`New`), `AlvoUpdated<AlvoRecord>` (`Old`, `New`),
  `AlvoDeleted<AlvoRecord>` (`Old`), `AlvoSaved<AlvoRecord>` (`New`, `Old` is `null` on create) — and any of
  `AlvoEventContext`, a `CancellationToken` and your own services. **A class** implementing
  `IAlvoEventHandler<TMessage>` is built per delivery from the delivery's own DI scope.
- **`when`** is a CEL condition over the images the verb's event carries: `new.` and `old.` on updates, `new.` on
  creates and saves, `old.` on deletes, `changed(field)` on updates, `@user` and `@tenant`. It is judged after the commit
  and before any delivery exists: an event it does not match costs nothing. An `OnSaved` condition reads only `new.` —
  use `OnUpdated` for a condition on the change. A `"*"` registration's condition tests only `@user` and `@tenant`.
- **Everything is checked when the host starts**, against your descriptor: an unknown entity, a typo in a condition, a
  condition reading what the event cannot carry or a field left out of the event images (`changed()` included), a
  service your container cannot provide, a timeout that is not positive or longer than an hour. All problems are
  reported in one refusal, each naming the handler and its slot — `extensions/ticket-resolved-to-chat/when`. Problems
  that do not depend on the descriptor — a malformed or repeated id, a missing service — refuse the start even before a
  dashboard-first host has a descriptor.

## What a delivery guarantees

- **At least once, with the same `EventId`.** A failure, a timeout or a process that stops mid-run means the handler
  runs again. Deduplicate on `context.EventId` before anything you cannot repeat.
- **Retries.** 5 s, 30 s, 2 min, 15 min, 1 h, 6 h (each spread by a fifth either way); after the seventh attempt the
  delivery is **dead**. Change it per handler with `options.Retry = AlvoRetryPolicy.From(…)` (no wait longer than
  7 days) or `AlvoRetryPolicy.None`.
- **Timeouts are enforced.** `options.Timeout` (30 s by default, at most 1 h) ends the attempt whether or not the
  handler observes its token: Alvo cancels the token and waits up to 30 s more. A handler that ends in that grace is
  recorded by its own result — succeeded, or failed with its own error — unless it ended by giving in to the
  cancellation, which is a `timeout`. A handler still running then is **abandoned, not stopped** — .NET cannot stop it:
  the attempt is recorded as a `timeout`, and the handler keeps running in the background, no longer counted against
  the concurrency limit, and can overlap its own retry.
- **A handler that keeps hanging stands down.** Once one handler has as many abandoned invocations still running as
  `Alvo:Deliveries:MaxConcurrency`, Alvo stops claiming that handler's deliveries — logged once, as a warning
  `HandlerStoodDown` — until one of them ends; every other handler keeps running. A handler that blocks its thread and
  ignores its token therefore strands a bounded number of thread-pool threads (fewer than twice `MaxConcurrency`), not
  one per attempt. Watch the `alvo.delivery.abandoned` counter, honour the token, and be idempotent on `EventId`.
- **A busy database does not cost an attempt.** When the database refuses the write that records an attempt — SQLite
  busy, a PostgreSQL deadlock or serialization failure — Alvo writes it again after a short wait, while the retry would
  still *start* inside the delivery's lease, and for at most 30 s after the first refusal (the first retry is logged as
  `DeliveryAnswerRetried`, then every tenth). On SQLite the retried write may then wait its turn at the write gate and
  land after the lease; the fence decides — it is recorded if no other worker has taken the delivery over, and changes
  nothing if one has. A delivery is never answered twice.
- **In order per record.** One record's events reach a handler in order — also when an earlier event of the record
  has not been fanned out yet because its processing failed or its dispatcher died — and a dead delivery holds that
  record's later events back, for that handler only. `options.Ordering = AlvoOrdering.None` opts out. Order is by event
  id, so two processes writing one record in the same millisecond can still interleave
  ([#150](https://github.com/Burgyn/MMLib.Alvo/issues/150)).
- **The order has a price until descriptor actions move onto deliveries.** An earlier event whose descriptor
  after-hook action keeps failing — a webhook endpoint that is down — holds the record's later handler deliveries back
  until it succeeds or the outbox gives up on it
  ([`Alvo:Events:MaxAttempts`](/reference/configuration/#alvoevents)): about 45 s per failing event at the defaults.
  The failing event's own delivery is not held.
- **A dead delivery blocks its record until it is cleared.** Redeliver, replay and pause arrive in a later release; until
  then an operator unblocks a lane by setting that row's `status` in `<prefix>_deliveries` to `'cancelled'`, or retires the
  whole handler with `AddRetiredExtension`. To run a dead delivery again instead, [reset it by hand](#retry-a-dead-delivery-by-hand).
- **Who the handler is.** By default the system, in the event's tenant (`'admin' in @user.roles` is true, another
  tenant's rows are invisible); `options.RunAs = AlvoRunAs.EventActor` acts as the caller who made the change.
  `context.Data` reads and writes as that caller, through the same rules and tenancy as any other call.
- **`EventActor` uses today's roles by name.** The roles the event recorded are looked up in the descriptor as it is
  now: a role redefined since the event grants its rules as they are now; a role it dropped is not held. A handler on
  an event the system made runs as `admin`, as the event did. An event whose tenant or caller cannot be read is never
  run as someone else: its delivery is dead with `event-unreadable`.
- **Loops stop.** A handler's writes and published events sit one hop deeper in the causation chain than the event that
  ran it — even through a DI-injected `IAlvoData` with a fresh `AlvoContext.System`. Past
  [`Alvo:Extensions:MaxDepth`](/reference/configuration/#alvoextensions) (8) the next delivery is recorded dead with
  `chain-depth-exceeded`, never run. The chain follows .NET's execution context: work you hand to your own queue
  leaves it.
- **An apply cannot unbind a handler.** An apply, a dry run, a rollback or `ApplyAlvoDescriptorAsync` that removes an
  entity or field a bound handler reads, or excludes a field its condition reads, is refused naming the handler
  ([details](/extending/extension-catalog/#an-apply-cannot-drop-what-a-handler-reads)). A handler that never bound — a
  dashboard-first host before its descriptor fits, a stored boot that ended `Failed` — blocks nothing: the dry run
  carries a warning, it is logged `ExtensionUnbound`, and every event it would have handled is recorded as a dead
  delivery with the reason `unbound`, which does not hold the record's later events back.
- **Nothing sensitive is stored.** A delivery records ids, statuses, times and an error **type** — never a body, a URL
  or an exception message. The type is the exception's type name, or one of `when-failed` (the condition threw),
  `timeout`, `chain-depth-exceeded`, `event-missing` (the envelope left the outbox), `event-unreadable`,
  `lease-expired` (its last attempt never answered — a handler that crashes its process, say), `retired` and
  `unbound`.

### Retry a dead delivery by hand

Setting a dead row back to `pending` alone does not retry it: a delivery that died at its last attempt keeps that
attempt count, so the next claim takes it past its policy and records it dead `lease-expired` without running it.
Reset the count too — and, because each attempt's number keys its row in `<prefix>_delivery_attempts`, delete the
delivery's attempt history in the same transaction. Here and below, `<prefix>` is your schema prefix
(`UseSchemaPrefix`) — `alvo` by default, so the tables are `alvo_deliveries` and `alvo_delivery_attempts`:

```sql
BEGIN;
DELETE FROM <prefix>_delivery_attempts WHERE delivery_id = '<delivery id>';
UPDATE <prefix>_deliveries
   SET status = 'pending', attempts = 0, claimed_by = NULL, lease_until = NULL,
       completed_at = NULL, last_error_type = NULL
 WHERE id = '<delivery id>' AND status = 'dead';
COMMIT;
```

The row keeps its event, its place in the record's order and its `not_before`, which is already past, so the next round
claims it. Its earlier attempts are gone from the history; HX-06's redeliver will keep them.

## Application events

`AddEventHandler(id, "orders.approved", (AlvoRecord payload, …) => …)` handles an event your code publishes with
`IAlvoEvents.PublishAsync`; `AddEventHandler<THandler>(id, "orders.approved")` takes an
`IAlvoEventHandler<AlvoRecord>` class. Its condition tests only `@user` and `@tenant`; check the payload inside the
handler. The `alvo.` namespace is reserved for events Alvo mints itself, and a host cannot publish into it.

## Rename or remove a handler

A host whose database holds unfinished deliveries — pending, running or retrying — for an id it no longer registers
refuses to start, naming the id, and changes nothing. Say what becomes of them:
`AddRetiredExtension("old-id", AlvoRetirement.DeadLetter)` keeps them as dead deliveries (`retired`);
`AlvoRetirement.Discard` cancels them.

A retirement is applied once, when the host starts, just before it reports ready. A delivery of that id still running
on another replica at that moment may finish its side effect; only its answer is ignored.

The same check refuses two starts you may not expect:

- **A rollback.** Going back to a build that does not know a handler a newer build added, while that handler still has
  unfinished deliveries, is refused like a removal: the older build can neither register nor retire an id it never
  knew. Roll forward instead; or drain first — let the handler's deliveries finish, or cancel them
  (`UPDATE <prefix>_deliveries SET status = 'cancelled' WHERE subscriber = '<id>' AND status IN ('pending', 'running', 'retrying')`)
  — before you roll back; or roll back to a build that carries `AddRetiredExtension("<id>", …)`.
- **Two applications over one database** — say the standalone image and an embedded host — that register different
  handlers. Each refuses the other's unfinished work. Register the same handlers in both, or give each its own
  database.

## Configuration

[`Alvo:Deliveries:MaxConcurrency`](/reference/configuration/#alvodeliveries) (16, from 1 to 256) bounds how many
deliveries one process runs at once, and how many abandoned invocations one handler may leave running before it stands
down. Deliveries share these with the outbox ([`Alvo:Events`](/reference/configuration/#alvoevents)):

- `Enabled`, `DispatchMode` and `PollInterval` — the same switch, mode and idle wait;
- `BatchSize` — the most deliveries one manual round (`DrainAsync`) claims;
- `MaxAttempts` and `ClaimLease` — not a delivery's own retries, which follow the handler's `Retry` policy, but how long
  an earlier event of a record that the outbox has not fanned out yet holds that record's ordered deliveries back.

A delivery's lease is not configured: a claim holds for the longest registered handler timeout plus 60 s (90 s at the
defaults), so an attempt that times out and settles is still answered inside it.

On SQLite, one process's writes to one database take turns — every write transaction Alvo's EF driver makes: the
outbox, the deliveries, every data write (a handler's included), schema changes, secrets, descriptor versions and
management idempotency records — instead of contending for the file's lock. A turn waits no longer than the
connection's busy timeout (`Default Timeout`, 30 s unless you set it) and then fails with the same "database is locked"
error SQLite gives. `Default Timeout=0` waits without bound, as SQLite itself then does — and then a delivery's answer,
and with it the host's shutdown, can wait behind a stuck writer until the host's shutdown timeout ends the process. Code that runs inside a write — a custom
CEL function — must not write through Alvo itself. PostgreSQL has no such turn.
