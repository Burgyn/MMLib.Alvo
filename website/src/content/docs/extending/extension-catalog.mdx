Code your host registers is part of the backend as much as the descriptor is. Alvo lists it — the dashboard, the
Management API and the schema assistant all read one **extension catalog** — and keeps the two from drifting apart: an
apply that would take away what a handler reads is refused, naming the handler.

## What is listed

Every [event handler](/extending/event-handlers/) and every [command](/extending/commands/) the host registers, as
**metadata, never code**: what it is, what it binds to and when it runs. Nothing in the catalog can change one; it is
changed in the host's C# and redeployed.

The condition is a lambda over the host's `Vehicle` class ([Typed or CEL](/extending/typed-or-cel/)), and the catalog
lists the CEL it was translated into when it was registered: `changed(status) && new.status == 'in_repair'`. Registered
over `Entity("vehicles", …)` with that text as a CEL string `when`, the handler is listed exactly the same.

| Member | What it says |
|---|---|
| `id` | the id the handler was registered under — its identity, and the key of its deliveries |
| `kind` | `eventHandler`, `command`, or a [write hook](/extending/write-hooks/)'s phase: `validate`, `beforeWrite`, `afterWrite`, `beforeDelete`, `afterDelete` |
| `stage` | `postCommit` for a handler: it runs after the write commits; `http` for a mapped command; `preTransaction` for an internal one, which runs in its invoker's flow before its own unit, and for a validate hook; `inTransaction` for the other write hooks |
| `entities` | the entities it binds; `["*"]` for an every-entity handler, `[]` for an application-event handler and for a command bound to no entity |
| `operations` | `create`, `update`, `delete`, as the policy names them; `OnSaved` lists `create` and `update`, and `OnUpdated`'s `update` covers a replace; `[]` for an application-event handler |
| `event` | the event type an application-event handler handles; `null` otherwise |
| `when` | its condition as CEL text — a lambda's translation, written canonically — or `null` |
| `order` | its place among the handlers of the same target: lower first, then registration order — the order the catalog lists them in |
| `timeout` | how long one attempt may take, as a `TimeSpan` (`"00:00:30"`) |
| `runAs` | `system` or `eventActor` |
| `ordering` | `perRecord` or `none` |
| `description` | the sentence you set in `options.Description`, or `null` |
| `typeName` | the class that implements it, only when the host exposes type names (below); a delegate is never named |
| `route` | a mapped command's route pattern, as mapped (a `MapGroup` prefix is not included); `null` otherwise |
| `httpMethod` | `POST` for a mapped command; `null` otherwise |
| `access` | a command's access rule as CEL text — a lambda's translation; `null` for a handler |
| `paused` | whether an operator paused the handler ([operate deliveries](/extending/operate-deliveries/#pause-and-resume)) |
| `topLevelOnly` | `true` for a validate hook: it runs only for a write no transaction unit is open around |
| `enabled` | `false` once an administrator switched a validate hook off ([Validate and guard writes](/extending/write-hooks/#validate-before-the-transaction)); `true` for everything else |

An id retired with `AddRetiredExtension` is not an extension and is not listed. `kind` and `stage` gain values as later
releases add kinds of host code; a typed .NET client older than the server cannot read a value it does not know, so a
client that must tolerate one reads the raw string.

## Read it

`GET /management/projects/<project>/extensions` answers any caller with the `viewer` level, and
`IAlvoManagement.GetExtensionsAsync` answers in process:

```json
{
  "items": [
    {
      "id": "book-repair",
      "kind": "eventHandler",
      "stage": "postCommit",
      "entities": ["vehicles"],
      "operations": ["update"],
      "event": null,
      "when": "changed(status) && new.status == 'in_repair'",
      "order": 0,
      "timeout": "00:00:30",
      "runAs": "system",
      "ordering": "perRecord",
      "description": "Books the vehicle into the workshop when it goes in for repair.",
      "typeName": null,
      "route": null,
      "httpMethod": null,
      "access": null,
      "paused": false,
      "topLevelOnly": false,
      "enabled": true
    }
  ]
}
```

- **Type names stay hidden by default.** `Alvo:Extensions:ExposeTypeNames` (`false`) fills `typeName` for a class
  handler. A type name reaches every catalog viewer and the assistant's model, and it describes your code's insides,
  so it is something you opt into. Descriptions are visible to every viewer too: put no secrets in them.
- **The capability report names the kind.** With at least one handler registered,
  `GET …/capabilities` lists `extensions.eventHandler` in `honoured`, after the descriptor's blocks — and
  `extensions.command` with at least one command, and `extensions.validate`, `extensions.beforeWrite` and so on with a
  write hook of that phase.
- **The policy simulator lists what would run.** `POST …/policy/simulate` answers with `extensions`: the entity's own
  handlers and write hooks, and the every-entity ones, whose `operations` contain the simulated operation. It answers with `commands` too:
  each command bound to the entity or to none, and whether the simulated caller passes its rule — `null` when the rule
  reads the row, which the simulator does not read.

## In the dashboard

**Schema** marks every entity host code runs on with a `⟨/⟩ n` badge, counting the entity's own handlers and every
every-entity one. Open the entity and its **Lifecycle** tab shows what runs *outside the write's transaction* — before-hooks,
which run inside the transaction, stay on **On write**:

- the descriptor's after-hooks, read-only, each with a link to **On write**, where they are changed;
- each handler, read-only and marked `⟨/⟩ from code`, with its description, its `when`, and a line such as
  `on update · timeout 30 s · runs as the system · in order per record`;
- in a host that maps a command, a **Commands** lane: each command bound to a row of the entity, read-only, with its
  route and its access rule.

In a host that registers a write hook, two lanes come first: **Before the transaction** holds the validate hooks,
marked *top-level writes only* and, when an administrator switched one off, *switched off*; **In the transaction** holds the
before/after write and delete hooks, each with its phase. Every write hook shows this instance's numbers, such as
`p95 4 ms · 0 rejections in 24 h`, once it has run; an operator the stats call refuses sees the lanes without them.
On **On write** and **Rules**, a note under each operation says how many write hooks also run on it — a switched-off
one does not count — and links here. The policy simulator lists the code that also runs on the simulated operation,
and an apply's preview lists the code bound to the entities its plan touches. A rename's plan line names only the new
entity, so the preview does not list the hooks bound to the old name; the apply still refuses to unbind them.

## An apply cannot drop what a handler reads

A handler binds to the descriptor when the host starts, and so does a write hook. Alvo then refuses any change that would
unbind either — a write hook by the entity it binds and the fields its condition reads:

| The change | Pointed at |
|---|---|
| removes an entity a handler binds | `/entities/<entity>` |
| removes or renames a field its condition reads, or retypes it so the condition no longer compiles | `/entities/<entity>/fields/<field>` |
| adds a field its condition reads to `events.exclude` | `/entities/<entity>/events/exclude/<index>` |
| removes or retypes a field its typed class maps, makes it optional under a non-nullable property, or drops an enum value one of the class's members maps | `/entities/<entity>/fields/<field>` |
| adds a field its typed class maps to `events.exclude` | `/entities/<entity>/events/exclude/<index>` |

The refusal is the `422` [`validation`](/reference/problem-types/#validation) problem any invalid descriptor gets, with
code `descriptor`. A field both read by the condition and mapped by the class gets the condition's sentence, once; a
mapped field's own sentence names the class — "its typed record Vehicle maps it". Beside each pointed violation travels the binding compiler's own sentence at `"pointer": ""`, so a
second cause is never hidden behind the first:

```json
[
  {
    "pointer": "/entities/vehicles/fields/status",
    "code": "descriptor",
    "message": "Field 'status' of 'vehicles' is bound by extension 'book-repair' (eventHandler, in this host): its condition reads it, so without it the handler would no longer bind, and every event it would have handled would be recorded dead.",
    "fixSuggestion": "Remove the registration and redeploy first, or keep the field."
  },
  {
    "pointer": "",
    "code": "descriptor",
    "message": "Extension 'book-repair' (eventHandler, in this host) would no longer bind to this descriptor — extensions/book-repair/when: …",
    "fixSuggestion": "…"
  }
]
```

- **Every path is guarded**: an apply, a dry run (and with it the dashboard's preview), a rollback and
  `ApplyAlvoDescriptorAsync`. The check runs right after validation and before the revision check, so a stale
  `If-Match` on such a change answers `422`, not `412`: the change could never apply.
- **It refuses a change, not a state.** A handler that never bound — a dashboard-first host's first descriptor, a stored
  descriptor the host started over and could not apply — blocks nothing. The dry run carries a warning instead, and the
  handler's events are recorded dead `unbound` until a descriptor fits it.
- **The remedy has an order**: remove or change the registration, redeploy the host, then apply.

The guard reads the catalog this process holds. Two applies racing before either publishes, or an apply on another

## The assistant

The [schema assistant](/guides/schema-assistant/) reads the catalog when it matters. `get_descriptor` answers with
`hostExtensions`, how many extensions run on each entity, and `get_extensions` lists them. Before proposing an
after-hook on an entity that count names, it reads the catalog and names an extension that already does what you asked
instead of adding a second one; and it does not propose removing a field an extension reads — the dry run would refuse
it anyway, naming the extension.
