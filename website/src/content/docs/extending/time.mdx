A booking needs a reminder a day before it starts, and the desk needs tomorrow's slots opened every night. Neither is a
reaction to a write alone: one must happen **at a time**, the other **regularly**. Alvo gives host code three tools for
that, and runs all three the way it runs an [event handler](/extending/event-handlers/) — as deliveries, with retries,
history, a dead letter and *run again*:

| You need | Use | Runs |
|---|---|---|
| Something once, at a time that depends on a record | a **timer** — `IAlvoScheduler.ScheduleAsync(key, at, …)` | the handlers of the event it fires |
| Something regularly | a **schedule** — `AddSchedule<TJob>(id, cron, timeZone)` | your `IAlvoScheduledJob` |
| A data fix-up once, after a descriptor revision | a **data migration** — `AddDataMigration<T>(id, afterRevision)` | your `IAlvoDataMigration` |

Timers, schedules and migrations live in the database beside the outbox, so they need a database driver (SQLite or
PostgreSQL); the in-memory `InMemoryAlvoData` has none.

## A keyed timer

A timer has a **key** you choose. Arming the same key again **moves** it; cancelling it deletes it. At its time it fires
an event — a custom event, here the typed `BookingReminderDue` — once, and every handler of that event runs.

- **Move = the same key.** `reminder:<booking id>` is armed on create and armed again when `starts_at` changes; one
  timer, at the latest time. A booking deleted takes its reminder with it.
- **Fires exactly once, handlers at least once.** The fire and the event's place in the outbox commit together, or
  neither does — a move or a cancel that lands while the timer is being fired wins, and the stale fire appends nothing.
  The handlers then run as deliveries, which are at least once: make them idempotent, as every handler.
- **A time already past fires on the next round.** Times are stored in UTC.
- **Keys** are 1–200 characters, none of them a control character. The event type must be your own — the `alvo.`
  namespace is refused.

### Inside a transaction

`ScheduleAsync` and `CancelAsync` called while a unit is open — a [`TransactAsync`](/extending/transactions/) delegate,
or a write hook — write through that unit's transaction: a rollback leaves no timer, and a commit arms it with the
rows.

### Tenants

A timer belongs to a tenant: the `tenant` argument, or else the open unit's tenant. On a descriptor with a tenant-scoped
entity one is required, and an argument that differs from the open unit's tenant is refused. The same key in two
tenants is two timers. The fired event carries the tenant, and its handlers run as the system in that tenant.

### Depth

A timer armed from a handler remembers the handler's correlation, causation and depth, and its event is one level
deeper than the handler. A handler already runs one level deeper than the event it handles, so a timer that re-arms
itself from its own handler climbs **two levels per cycle**: at the
[chain-depth limit](/extending/#one-limit-already-enforced) of 8 (the default) it fires about four times, then stops
with a dead `chain-depth-exceeded` delivery, as an event loop does. `ScheduleAsync` itself is refused past the limit.

## Schedules

<SourceExcerpt code={reminders} from="public sealed class RollSlots" title="BookingReminders.cs" />

`AddSchedule<RollSlots>("roll-slots", "0 2 * * *", "Europe/Bratislava")` (in the registration above) runs the job at
02:00 Bratislava time every night.

- **Cron** is the standard five fields (minute, hour, day of month, month, day of week) — no seconds. The **zone** is
  an IANA id. Both are checked at start, and every problem is reported at once.
- **Daylight saving time**, as [Cronos](https://github.com/HangfireIO/Cronos) defines it: a time in the spring-forward
  gap runs at the end of the gap; in the fall-back overlap a fixed time runs once, and an hourly (or wildcard-hour)
  schedule runs in both hours.
- **One run across replicas.** Each occurrence is claimed by one process and advanced in the same transaction that
  queues its run; three replicas racing it produce one run.
- **Missed occurrences run once.** A host that was down over several occurrences runs the job once when it comes back,
  then continues from the next one — no backlog.
- **Each run is a `schedule` delivery** with retries (`options.Retry`) and a timeout (`options.Timeout`, 15 minutes by
  default). A run that fails for good is dead, and the next occurrence still runs. Jobs take their own pool,
  [`Alvo:Deliveries:MaxJobConcurrency`](/reference/configuration/#alvodeliveries) (2 by default), so a long job never
  takes an event handler's slot.
- **`AlvoJobContext`** says which occurrence this is (`ScheduledFor`), which tenant (`Tenant`), which attempt, and gives
  the run a data session as the system in that tenant (`Data`).
- **Per tenant.** `options.Scope = AlvoScheduleScope.EachTenant` runs one run per tenant, each reading only its own
  rows. Alvo does not know your tenants: register an `IAlvoTenantCatalog` that lists them, or the host refuses to start.
- **Run now.** The dashboard's *Run now*, or `POST …/schedules/{id}/run` (the `developer` level), starts one run
  outside the cron; the next occurrence stays where it was. On `EachTenant` it starts one run per tenant, and answers
  409 when the catalog lists no tenants.

### Changing and removing a schedule

Each host process records the schedules it registers when it starts. A changed cron or zone moves the next run; an
unchanged one keeps it. **Removing a schedule from code does not delete its stored row** — another replica may still
run the old build. The row is inert: nothing runs it and the catalog does not list it. Declare the id retired with
`AddRetiredExtension` to delete it. Keep a schedule's cron and zone identical across hosts: two processes that
register one id differently overwrite each other at start.

## Data migrations

`AddDataMigration<BackfillCodes>("backfill-codes", afterRevision: 4)` runs `BackfillCodes` once, as a `migration`
delivery, after the descriptor reaches revision 4 — at the boot or the apply that gets there, within one poll of the
schedule pump. A rollback below revision 4 neither undoes it nor runs it again on a later re-apply.

It starts at the first revision Alvo reads at or after 4 — a revision *number* reached, not a shape: if a rollback
lands first, it runs over the older shape, so check for the fields you need.

When that revision's descriptor has a tenant-scoped entity, a migration runs **once per tenant** your
`IAlvoTenantCatalog` lists, each as the system in that tenant, so no run reads another tenant's rows. Without a catalog
the host refuses to start while such a migration has not yet started. A tenant created after the migration started
does not get it — make the fix-up part of creating a tenant if it must. With no tenants at all the migration counts as
done, and the log says so.

A start that fails — the tenant list throws, say — is logged and that migration alone is tried again after a minute,
then two, up to 15; the other migrations go on. A migration cannot be run now: it runs once per revision.

## In the dashboard

*Operations* lists the schedules and data migrations under the handlers: the cron and zone (or the revision a
migration waits for), the next run in the schedule's own zone, the last run and its outcome, and **Run now** for a
schedule. A *Timers* tile counts the armed timers and how many are due — a due count that stays above zero means
nothing is firing them. Each run is a delivery in the list beside it, with its attempts.

## Limits

- No sub-minute cron: use a timer.
- No backlog: a missed occurrence runs once.
- A run that outlasts its period overlaps the next occurrence's.
- A data migration that needs a view across tenants cannot have one.
