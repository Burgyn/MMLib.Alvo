Q1  D1's monotonicity claim DOES NOT SURVIVE as written. .NET's Guid.CreateVersion7() has no
    monotonic counter: it fills everything below the 48-bit millisecond with random data, so
    same-millisecond ordering is NOT guaranteed, and it is not even biased.
      "Q1 v7 'D' ordinal inversions over 100000: 49839"
      "Q1 v7 'N' ordinal inversions over 100000: 49898"
      "Q1 adjacent pairs minted in the SAME millisecond: 99961; inversions among them: 49839 (49.9%)"
      "Q1 adjacent pairs minted ACROSS a millisecond boundary: 38; inversions among them: 0"
      "Q1 two ids minted in ONE millisecond (CreateVersion7(fixed), 1000 calls): inversions 515 of 999 pairs"
    The 'D' and 'N' spellings are equally affected - the spelling is a Q2 question, not a Q1 one.
    ORDER BY id is therefore monotone to the MILLISECOND and arbitrary inside one.
    Cost to a dispatcher that orders by it: two events written to the same entity key inside one
    millisecond are dispatched in arbitrary relative order, on ONE dispatcher, with no second
    replica involved. Per-entity-key ordering does not hold merely "while exactly one dispatcher
    runs"; it holds while one dispatcher runs AND no two events for one key land in one
    millisecond. The plan and the addendum both state the weaker condition only.
    Also measured, because it decides how the column may ever be typed: Guid's DEFAULT byte order
    is not time-sortable, so the id is safe as TEXT and unsafe as a BLOB written from ToByteArray().
      "Q1 'D' string form inversions           : 4993 / 9999"
      "Q1 ToByteArray() (little-endian) inversions: 5050 / 9999   <- Guid's DEFAULT byte order is NOT time-sortable"
      "Q1 ToByteArray(bigEndian: true) inversions : 4993 / 9999"
    A fix exists and costs nothing at the DDL - an in-process monotonic wrapper that bumps the
    random tail whenever the millisecond repeats:
      "Q1 in-process MONOTONIC v7 (bump the random tail on a repeated ms) inversions over 100000: 0"
    It removes in-process ties only; two processes minting inside one millisecond still interleave,
    which is the guarantee level D1 already states it has.
    Clock regression, measured deterministically through the CreateVersion7(DateTimeOffset)
    overload rather than by touching the system clock:
      "Q1   ORDER BY id puts the later id first: True"
    A backwards clock step reorders the queue by exactly the size of the step. It cannot lose an
    event - the claim filters dispatched_at IS NULL and never a watermark, so R2 stays closed -
    and it cannot stall one, because a lower id is claimed sooner rather than skipped.

Q2  D1's cross-engine ordering claim SURVIVES, on both spellings, under the collation that was
    the named risk.
      "Q2 SQLite 'D': engine ORDER BY matches .NET ordinal: True; first divergence at none"
      "Q2 SQLite 'N': engine ORDER BY matches .NET ordinal: True; first divergence at none"
      "Q2 PostgreSQL 'D': engine ORDER BY matches .NET ordinal: True; first divergence at none"
      "Q2 PostgreSQL 'N': engine ORDER BY matches .NET ordinal: True; first divergence at none"
      "Q2 PostgreSQL ORDER BY id COLLATE "C"     matches .NET ordinal: True; first divergence at none"
      "Q2 PostgreSQL ORDER BY as_uuid            matches .NET ordinal: True; first divergence at none"
    Measured under datcollate=en_US.utf8 - NOT C or POSIX - which is postgres:16-alpine's real
    default, printed in the engine facts above so the result is attributable. The fallback to
    Guid.ToString("N") is therefore not needed, and neither is a COLLATE spelling.
    Why it holds, so nobody generalises it too far: every UUID text form is fixed width with its
    hyphens at fixed positions, so even a punctuation-insensitive collation folds to the same
    relative order as byte comparison. That is a property of fixed-width keys, not of en_US.utf8.

Q3  D2's portable claim statement SURVIVES, and R4's finding is confirmed with two corrections.
      "Q3 SQLite: UPDATE ... ORDER BY ... LIMIT (R4 predicts a SQLite syntax error) — REFUSED: SQLite Error 1: 'near "ORDER": syntax error'."
      "Q3 PostgreSQL: UPDATE ... ORDER BY ... LIMIT (R4 predicts a SQLite syntax error) — REFUSED: 42601: syntax error at or near "ORDER""
    Correction 1: the message names ORDER, not "limit" as R4 records - SQLite parses left to
    right and dies on the first illegal clause. Correction 2: PostgreSQL refuses the same
    statement, so the subquery LIMIT is portability rather than a SQLite workaround. The bundled
    build confirms the compile flag is unset:
      "compile_options with UPDATE_DELETE_LIMIT: 0"
    RETURNING order is arbitrary in practice and not only on paper, on BOTH engines, so the
    in-process re-sort is load-bearing:
      "Q3 SQLite: portable claim returned 10 rows; RETURNING already sorted: False; claimed the 10 lowest ids: True"
      "Q3 PostgreSQL: portable claim returned 10 rows; RETURNING already sorted: False; claimed the 10 lowest ids: True"

Q4  D2's claim SQL, AS THE PLAN WRITES IT, IS WRONG: two claimants deliver every row twice.
      "Q4 [as the plan writes it] B still blocked while A holds its rows: True"
      "Q4 [as the plan writes it] A claimed 10, B claimed 10, overlap 10 (must be 0); rows with attempts > 1: 10 (must be 0)"
    B blocks exactly as D2 predicts, but when the lock clears under READ COMMITTED it re-checks
    only the OUTER WHERE, which in the plan's SQL is nothing but `id IN (subquery)` - the
    subquery's own `claimed_at IS NULL` is not part of it. So every row is claimed twice and
    attempts is incremented twice. D2's stated cost, "a second instance is slow, not incorrect",
    is false for that statement.
    The one-line amendment measured green in the same run - repeat the predicate in the outer
    WHERE, so the subquery chooses and the outer WHERE re-validates under EvalPlanQual:
      "Q4 [WITH the outer claimed_at IS NULL] A claimed 10, B claimed 0, overlap 0 (must be 0); rows with attempts > 1: 0 (must be 0)"
    The statement Task 5 must use, which both engines accept (see the two Q3 lines ending
    "the Q4 variant) - ACCEPTED"):
      UPDATE {outbox} SET claimed_at = @claimed_at, claimed_by = @claimed_by,
                          attempts = attempts + 1
       WHERE dispatched_at IS NULL
         AND (claimed_at IS NULL OR claimed_at < @stale_before)
         AND id IN (SELECT id FROM {outbox}
                     WHERE dispatched_at IS NULL
                       AND attempts < @max_attempts
                       AND (claimed_at IS NULL OR claimed_at < @stale_before)
                     ORDER BY id
                     LIMIT @batch)
      RETURNING id, event_type, partition_key, payload, attempts
    This is a change to a ratified decision, not an implementation detail, and it is the one
    finding in this spike that the plan itself declared blocking.

Q5  THE WAL STOP-CONDITION DID NOT TRIGGER. journal_mode=WAL is required nowhere, and the shared
    SQLite registration is not changed.
      "journal_mode       : delete"
      "busy_timeout       : 0 ms"
      "DefaultTimeout     : 30 s"
      "Q5 [the SHIPPED registration (no journal_mode pragma at all)] one-statement claim on the shipped connection string: SUCCEEDED with 10 rows after 1059 ms of waiting"
      "Q5 [the SHIPPED registration (no journal_mode pragma at all)] the dispatcher's BeginTransaction + claim on the shipped connection string (no busy_timeout pragma): SUCCEEDED after 1058 ms of waiting"
      "Q5 [the SHIPPED registration (no journal_mode pragma at all)] the REQUEST PATH beginning its own transaction while the dispatcher holds a claim: SUCCEEDED after 1059 ms of waiting"
    A clean wait, not SQLITE_BUSY, in both directions: whichever writer arrives second blocks for
    as long as the first holds its transaction and then succeeds.
    Correction to R5: it is not true that there is "no Default Timeout anywhere". Microsoft.Data
    .Sqlite's DefaultTimeout is 30 s by default and its retry loop covers BEGIN as well as the
    statement, which is what already makes the shipped configuration correct. An explicit
    PRAGMA busy_timeout=5000 changes nothing measurable:
      "Q5 [the SHIPPED registration (no journal_mode pragma at all)] the dispatcher's BeginTransaction + claim on PRAGMA busy_timeout=5000: SUCCEEDED after 1048 ms of waiting"
    R5's mechanism is real, but exactly ONE shape reaches it - a DEFERRED transaction that READS
    and then WRITES:
      "Q5 [WAL] a DEFERRED read-then-write dispatcher transaction, after another connection committed a write in between (it committed: True): REFUSED after 30036 ms — SqliteErrorCode=5 Extended=517: SQLite Error 5: 'database is locked'."
    Extended code 517 is SQLITE_BUSY_SNAPSHOT: retrying cannot fix it, and those 30 s are the
    retry loop failing uselessly. In the shipped journal mode the same shape fails the OTHER
    party instead, which is worse, because the other party is the request path:
      "Q5 [the SHIPPED registration (no journal_mode pragma at all)] a competing autocommit write, while the dispatcher holds an open DEFERRED READ transaction: REFUSED after 31314 ms — SqliteErrorCode=5 Extended=5: SQLite Error 5: 'database is locked'."
    So WAL does not fix this shape; it only moves whose write fails. The binding constraint is
    therefore on Task 5's dispatcher, not on any registration: the claim must be a single write
    statement on an autocommit connection, or the first statement of a write-first transaction,
    and never preceded by a read inside the same transaction.
    Recorded for whoever revisits WAL later:
      "Q5 [WAL] PRAGMA journal_mode=WAL answered 'wal' (a journal-mode change is PERSISTENT in the database file)"
    - a journal-mode change is not a connection-string decision that a redeploy can revert.

Q7  D1's rejection of created_at as the ordering key is confirmed, and the margin is not close.
      "Q7 distinct 'O' stamps over 10000 successive GetUtcNow(): 495; largest tie run: 26"
      "Q7 distinct stamps at millisecond precision: 3; largest tie run: 9998"
    StoredInstant renders the full "O" form, so the first line is the one that applies to a real
    column: 10 000 successive reads of the clock produce 495 distinct values, with runs of 26
    identical stamps - the clock is nanosecond-scaled (TimestampFrequency 1000000000) but not
    nanosecond-resolved. Truncated to milliseconds it collapses to 3 distinct values, which is what
    any wire or JSON rendering would carry. On top of that StoredInstant binds ONE instant per write
    (data-path.md:354), so inside a write the ties are structural rather than merely likely.
    created_at is not a candidate for the ordering key at either precision.
